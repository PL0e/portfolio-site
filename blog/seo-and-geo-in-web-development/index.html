SEO and GEO in Web Development: Building Sites That Rank and Get Cited

How semantic HTML, server rendering, Core Web Vitals, and structured data decide whether Google ranks your pages and whether AI answer engines quote them.

Introduction

For twenty years, search meant ten blue links. A user typed a query, a search engine retrieved a ranked list of pages, and the user clicked through to read. Your job as a developer was to make that page crawlable, fast, and relevant enough to earn a high slot on the list.

That model still exists, but it is no longer the only one. ChatGPT, Perplexity, Google's AI Overviews and AI Mode, Gemini, and Claude now answer many questions directly. They read several sources, synthesize one response, and cite a handful of pages along the way. Often the user never sees a results page at all.

The shift is from retrieval to synthesis. A search engine retrieves documents and lets the human assemble the answer. An answer engine assembles the answer itself and decides which sources deserve credit. That changes what "visible" means. Ranking first matters less if the answer is written above the links; being the source the answer quotes matters more.

For developers, the consequence is concrete. The same things that always helped crawlers, such as clean HTML, fast server responses, and explicit structure, now decide whether a language model can parse your page, trust it, and lift an accurate passage from it. SEO and GEO in web development are no longer two disciplines. They are one engineering practice with two audiences: ranking algorithms and generative engines.

Section 1: The evolution from SEO to GEO

What SEO means in modern web development

Modern technical SEO is the work of making a site easy for search engines to find, render, understand, and trust. In practice it rests on four pillars:

  • Crawlability: bots can reach every important URL through links, a sitemap, and a robots.txt that blocks only what it should.
  • Indexability: each page returns the right status code, has one canonical URL, and isn't hidden behind noindex, login walls, or client-only rendering.
  • Speed and experience: pages meet Google's Core Web Vitals thresholds: Largest Contentful Paint (LCP) under 2.5 s, Interaction to Next Paint (INP) under 200 ms, and Cumulative Layout Shift (CLS) under 0.1.
  • Meaning: semantic HTML and structured data (schema.org in JSON-LD) tell the engine what each page is about and how its entities relate.

None of that is new. What is new is that a second kind of reader now consumes the same output.

What is generative engine optimization?

Generative engine optimization (GEO) is the practice of making content easy for AI answer engines to retrieve, understand, and cite when they generate a response. The term comes from a 2023 research paper by Aggarwal and colleagues, GEO: Generative Engine Optimization, which found that adding citations, quotations, and statistics to source content measurably increased how often generative engines surfaced it.

Generative engines work differently from a ranked index:

  1. Retrieve. The engine runs one or more searches, often several reformulated queries, and fetches candidate pages.
  2. Extract. It splits those pages into passages and keeps the ones that best match the question.
  3. Synthesize. A language model writes a single answer from those passages.
  4. Attribute. It links the sources it relied on, usually only a few.

The unit of competition shrinks from the page to the passage. A page can rank well and still never be cited if no single passage answers the question cleanly. A smaller site can be cited often if its passages are precise, verifiable, and easy to extract.

SEO vs. GEO at a glance

Comparison of traditional SEO and generative engine optimization

The overlap is the point. Almost every GEO lever is an SEO lever done more rigorously.

Section 2: Technical foundations for dual optimization (SEO + GEO)

Semantic HTML: structure that machines can read

Semantic HTML is the cheapest, highest-leverage optimization you control. When a crawler or an AI pipeline converts your page into text, it uses your tags to decide what is navigation, what is the main content, and how ideas nest. A page built from anonymous <div>s forces it to guess.

  • <main> and <article> mark the content worth extracting, so boilerplate is easier to discard.
  • <nav>, <header>, <footer>, and <aside> label the chrome that should not be quoted as an answer.
  • <section> with a heading groups one idea, which maps neatly onto the passages a retrieval system chunks.
  • One <h1>, then <h2>–<h6> in order gives a real outline. Never skip levels to get a smaller font; style with CSS instead.
  • Lists, tables, <figure>/<figcaption>, <time datetime>, and <dl> carry structure that survives conversion to text, unlike visual layouts.
<main>
  <article>
    <header>
      <h1>SEO and GEO in Web Development</h1>
      <p>By <a href="/about">Glendell S. Dia</a> ·
         <time datetime="2026-10-18">October 18, 2026</time></p>
    </header>

    <section aria-labelledby="what-is-geo">
      <h2 id="what-is-geo">What is generative engine optimization?</h2>
      <p>Generative engine optimization (GEO) is the practice of making content
         easy for AI answer engines to retrieve, understand, and cite.</p>
    </section>
  </article>
</main>

Performance and Core Web Vitals: speed is access

Speed used to be a ranking tiebreaker. For AI retrieval it is closer to a gate. Answer engines fetch pages at question time and under tight latency budgets, so a slow origin can simply time out of the candidate set.

  • Server-side rendering (SSR) sends complete HTML on the first response, so the text exists before any JavaScript runs.
  • Static site generation (SSG) and incremental static regeneration (ISR) pre-build pages and refresh them in the background, which gives CDN-cached speed with reasonably fresh content.
  • A low Time to First Byte (TTFB) comes from edge caching, efficient data fetching, and avoiding blocking work in the request path. Aim for under 800 ms, Google's "good" threshold.
  • Core Web Vitals (LCP, INP, CLS) remain Google ranking signals, and the same habits that pass them, such as optimized images, minimal render-blocking resources, and reserved space for media, also make pages cheaper for any bot to process.

JavaScript rendering pitfalls for AI crawlers

Googlebot renders JavaScript, though in a deferred second wave. Many AI crawlers, including OpenAI's GPTBot and Anthropic's ClaudeBot, have been observed fetching raw HTML without executing JavaScript. If your single-page application ships an empty <div id="root"></div> and builds everything client-side, those crawlers may see a blank page.

Common client-side rendering (CSR) failure modes:

  • Empty shell HTML: the main content, headings, and links exist only after hydration.
  • Client-only routing: URLs that resolve only inside the app, with every path returning the same shell.
  • Content behind interactions: text revealed by tabs, accordions, or "load more" buttons that fetch on click.
  • Metadata injected late: titles, canonical tags, and JSON-LD added by JavaScript after load.

The fix is to render meaningful HTML on the server: SSR or SSG with frameworks such as Next.js, Nuxt, Astro, SvelteKit, or Remix; prerendering for marketing routes; or at minimum server-rendered metadata and a <noscript> summary. Test it the way a bot sees it:

# What does a non-rendering crawler receive?
curl -s -A "GPTBot" https://example.com/blog/seo-and-geo | grep -i "<h1"

If your headline isn't in that output, neither is your chance of being cited.

Section 3: Content structure and information architecture for AI citations

Writing citation-worthy copy

A language model cites the passage that answers the question most clearly and with the least risk of being wrong. Write for that.

  • Factual density: prefer specific numbers, names, versions, and dates over adjectives. "INP under 200 ms" beats "fast interactions."
  • Verifiable claims: link primary sources such as specs, documentation, and research, and quote them accurately.
  • Self-contained passages: each paragraph should make sense when lifted out alone. Repeat the subject instead of relying on "this" or "it" from three paragraphs earlier.
  • Authoritative, neutral tone: state what is true and under what conditions. Hedge only where real uncertainty exists.
  • No fluff: intros that restate the title and filler like "in today's fast-paced digital world" dilute the passages a retriever scores.
  • Visible expertise: author names, bylines, credentials, and "last updated" dates help both Google's quality systems and an engine deciding whom to trust.

The direct-answer format

Put the answer first. Under every question-shaped heading, the first one or two sentences should answer it completely, and supporting detail follows.

<h2>What is generative engine optimization?</h2>
<p>Generative engine optimization (GEO) is the practice of making content
   easy for AI answer engines to retrieve, understand, and cite. It extends
   technical SEO from ranking pages to being quoted inside AI answers.</p>
<!-- Then: how it works, examples, caveats -->

This mirrors how featured snippets were won for years, and it maps directly onto passage extraction: the heading matches the user's question, and the sentence beneath it is a ready-made citation.

JSON-LD structured data: machine-readable context

Structured data turns implicit meaning into explicit facts: who wrote this, when, about what, for which organization, and where it sits in the site. Use JSON-LD in a <script type="application/ld+json"> block, rendered on the server.

  • Article / BlogPosting: headline, author, dates, image, publisher.
  • Organization or Person: the entity behind the content, with sameAs links to official profiles.
  • BreadcrumbList: the page's place in your hierarchy.
  • FAQPage: question-and-answer pairs. Since 2023 Google shows FAQ rich results mainly for well-known government and health sites, but the markup still gives machines clean Q&A pairs.
{
  "@context": "https://schema.org",
  "@graph": [
    {
      "@type": "BlogPosting",
      "headline": "SEO and GEO in Web Development",
      "description": "How to build sites that rank in search and get cited by AI answer engines.",
      "datePublished": "2026-10-18",
      "dateModified": "2026-10-18",
      "author": { "@type": "Person", "name": "Glendell S. Dia", "url": "https://pl0e.github.io/portfolio-site/" },
      "mainEntityOfPage": "https://pl0e.github.io/portfolio-site/blog/seo-and-geo-in-web-development/"
    },
    {
      "@type": "BreadcrumbList",
      "itemListElement": [
        { "@type": "ListItem", "position": 1, "name": "Home", "item": "https://pl0e.github.io/portfolio-site/" },
        { "@type": "ListItem", "position": 2, "name": "Blog", "item": "https://pl0e.github.io/portfolio-site/blog/" }
      ]
    },
    {
      "@type": "FAQPage",
      "mainEntity": [{
        "@type": "Question",
        "name": "What is generative engine optimization?",
        "acceptedAnswer": { "@type": "Answer", "text": "GEO is the practice of making content easy for AI answer engines to retrieve, understand, and cite." }
      }]
    }
  ]
}

Two rules keep structured data honest. Mark up only what is visible on the page, since markup that contradicts the content can be ignored or penalized. And keep it in sync with the content source, ideally generated from the same data, never hand-maintained separately.

Section 4: Developer checklist for 2026 and beyond

Treat visibility like accessibility or security: a set of checks that runs on every pull request, not a quarterly audit.

Crawling and access

  • Manage robots.txt as code. Keep it in the repo, review changes in PRs, and decide explicitly which AI user agents to allow, such as GPTBot, OAI-SearchBot, ClaudeBot, PerplexityBot, and the Google-Extended token. Blocking search-oriented bots also removes you from their answers.
  • Generate the XML sitemap at build time from your routes or CMS, with accurate lastmod dates, and fail the build if it is empty or contains non-canonical URLs.
  • Ping changes with IndexNow (supported by Bing and others) when content publishes or updates.
  • Return correct status codes: real 404s and 410s, 301s for moved content, and no soft-404 shells.
  • Keep staging out of the index with authentication or noindex headers enforced by environment, never by memory.

Rendering and performance

  • Assert server-rendered content in tests: fetch key routes without JavaScript and check that the <h1>, main copy, and JSON-LD are present.
  • Set performance budgets in CI with Lighthouse CI or similar: LCP under 2.5 s, CLS under 0.1, and bundle-size limits per route.
  • Track real-user Core Web Vitals (field data, including INP) and alert on regressions after deploys.
  • Cache aggressively at the edge and watch TTFB on dynamic routes.

Markup and metadata

  • Lint HTML semantics: one <h1>, no skipped heading levels, landmarks present, images with alt.
  • Validate JSON-LD on every build against schema.org types and your own required fields, such as headline, author, datePublished, and image for articles.
  • Map schema in your headless CMS: model authors, dates, FAQs, and breadcrumbs as structured fields so markup is generated from content, not typed by hand.
  • Check unique titles, meta descriptions, and canonicals across all routes, and flag duplicates in CI.
  • Generate Open Graph and social metadata from the same source as the page content.

Content and measurement

  • Add a direct-answer check to content review: does the first sentence under each heading answer it?
  • Show bylines and dateModified, and update them only when content materially changes.
  • Measure AI referrals: segment analytics traffic from chatgpt.com, perplexity.ai, gemini.google.com, and claude.ai, and track citations of your brand in the answer engines you care about.
  • Consider an llms.txt file that summarizes your key pages for language models. It is an emerging proposal, not a standard any engine guarantees to use, so treat it as low-cost and optional.
# Example CI job (GitHub Actions)
seo-geo-checks:
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v4
    - run: npm ci && npm run build
    - run: npm run test:ssr-content     # curl key routes, assert <h1> + JSON-LD
    - run: npm run lint:html            # headings, landmarks, alt text
    - run: npm run validate:jsonld      # schema checks on built pages
    - run: npx lhci autorun             # performance budgets

Conclusion

The line between "building the site" and "getting the site found" has disappeared. Search engines and generative engines read the same HTML, hit the same servers, and parse the same structured data. What they reward is also the same: pages that render fully on the first response, load fast, say clearly what they are, and back their claims with specifics.

That means the levers sit with developers. Semantic HTML, server-side rendering, Core Web Vitals, structured data markup, and LLM-friendly web architecture are not a marketing add-on bolted on before launch. They are the product's interface to every machine that decides whether a person will ever see it.

Code quality, site architecture, and content clarity are no longer separate from visibility. They are the visibility strategy. Build pages a machine can understand in one pass, write passages worth quoting, and both the ranking algorithms and the answer engines will have every reason to send people your way.
